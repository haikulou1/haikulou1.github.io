# loop 登录 - 需求澄清分析（loop-1）

> 阶段：需求澄清 | 技能：brainstorming | 日期：2026-08-06
> 本文档为设计阶段产物，不含代码变更。交互门控已静默接管自主决策。

## 1. 需求通览

「loop 登录」需求结构完整，含 8 章节 + 3 关键设计点。核心链路：
输入校验 → 凭证比对（加盐哈希）→ 登录态签发 → 登录态维持（Cookie HttpOnly+Secure+SameSite）→ 退出登录。
安全约束：防账号枚举（账号不存在/密码错误统一返回）、暴力破解防护（失败次数限制+验证码+IP限流）。
范围明确排除：注册、找回密码、SSO、第三方登录、扫码、MFA（均列入后续规划）。

## 2. 阻断性 Blocker 清单（blocker_count = 4）

以下 4 项无法靠自主决策合理闭环，必须上游（产品/技术/数据）输入：

### Blocker-1：账号禁用场景 vs 防账号枚举（真实矛盾）
- **矛盾**：需求第4章将「账号禁用」列为异常场景之一，但关键设计点要求「账号不存在与密码错误统一返回账号或密码错误」以防枚举。
- **未定**：禁用账号尝试登录时应返回什么？
  - 若返回「账号已禁用」→ 泄露账号存在性，违反防枚举原则；
  - 若统一返回「账号或密码错误」→ 无法告知用户禁用状态，用户体验与合规告知缺失。
- **需澄清**：禁用账号登录响应口径（是否允许区分告知 / 或统一模糊 + 后置通知渠道）。

### Blocker-2：登录态维持机制（Session vs JWT）与多端兼容范围未定
- **未定**：登录态基于服务端 Session 还是 JWT？需求仅建议 Cookie 属性，未定机制类型。
- **影响面**：退出实现（Session 删除 vs JWT 黑名单/短期）、记住我实现、分布式多实例会话共享、跨端。
- **未定**：兼容性非功能需求笼统，未列具体端（Web / APP / 小程序）。小程序不支持 Cookie，直接决定登录态方案。
- **需澄清**：登录态机制选型 + 目标终端范围（是否含无 Cookie 端）。

### Blocker-3：暴力破解锁定维度/阈值 与 防枚举交互未定
- **未定**：锁定维度（账号锁定 vs IP 锁定 vs 双维度）、失败阈值、锁定时长、解锁方式（自动超时 vs 管理员手动）。
- **张力**：账号级锁定本身可能泄露账号存在性（账号被锁=账号存在），与防枚举存在交互，需明确口径。
- **未定**：验证码类型（图形/滑动/行为）与触发条件（失败几次后出现）。
- **需澄清**：锁定与限流的具体策略参数（或确认按行业最佳实践自主决策）。

### Blocker-4：现有用户体系/数据结构依赖未明确
- **未定**：是否已存在用户表与密码字段？密码存储现状（明文/旧哈希）是否需迁移？用户唯一标识（用户名/邮箱/手机号）？
- **影响**：决定是否新建表、是否需密码哈希迁移脚本、凭证比对实现细节。
- **需澄清**：现有用户数据模型与密码存储现状（loop-1 无输入，无法从代码推断）。

## 3. 可自主决策项（非 blocker，记录决策供后续采纳）

按自主决策优先级 #②#③ 预置，上游未否决则采纳：

| 决策项 | 采纳值 | 依据 |
|---|---|---|
| 密码哈希算法 | Argon2id（bcrypt 作为兼容回退） | 行业最佳实践，OWASP 推荐 |
| 记住我时长 | 短 2h（会话 Cookie）/ 长 30d（持久 Cookie） | 行业惯例 |
| 密码强度校验 | ≥8 位，含字母+数字 | 通用基线 |
| Cookie 属性 | HttpOnly + Secure + SameSite=Lax | 需求已明示 + 安全默认 |
| HTTPS 部署 | 假设支持（Secure Cookie 前提） | 部署环境基线 |
| 登录入口 | 独立登录页 | 默认形态 |
| 技术栈 | 通用 Web 栈（待 Blocker-2/4 确认后细化） | 非登录需求特有决策 |
